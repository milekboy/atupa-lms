# Admin Step 9 — reporting, moderation, alerts and activity

Supported frontend delivered 18 November 2026. The plan checkbox remains open for the deployment gates below. This repository contains the LMS frontend; implementing these routes cannot establish missing backend capture, email jobs, detectors or storage policy.

## Implemented

- Learners and parents have `/dashboard/safety`: documented teacher, course, class and school targets, reason/note, reference receipt and paginated My reports with handled state. The browser cannot choose a reporter ID, severity, due time, assignee or status. Backend target validity/access checks remain authoritative.
- Context links fill the target ID: learner course pages and class details (class/teacher/school), learner school details, public outlines for signed-in learners/parents and parent linked-child course cards. General reporting also allows a known target ID without inventing a teacher/school directory or widening family/class access.
- Super Admin has `/admin/safety-reports`: unresolved/all queue, reported severity/assignee/due time/overdue flag, detail, internal comments, assignment and resolution. The current detail is fetched again before every action, must match the selected ID and must still be unresolved. Only known outcomes returned in `allowedOutcomes` can be selected or submitted. A reason and typed reference confirm resolution. Assignee defaults to the current admin; the entered ID must resolve to an active Super/Support account and still pass backend assignment authorization.
- Writes use explicit payload fields. Assignment/comment/resolution responses are reconciled against a fresh detail read, including actual operator/outcome/time for resolution. Network/server uncertainty prompts reconciliation and locks pending repeat submission. No success is fabricated from an optimistic browser state.
- Report receipts/history omit reporter IDs/names, internal notes/comments and attachments. Admin detail excludes attachment source URLs and requires ownership metadata; the target owner or reporter cannot use these new moderation responses for their own case. Another admin must handle it. This is additional frontend protection; deployed backend access and privacy across every delivery channel still need acceptance.
- `/admin/alerts` shows returned signals, severity, occurrences and limited documented detail fields; it supports only the documented acknowledged status plus note. The saved ID/status/note/operator are checked. Acknowledgement does not claim the underlying issue has been resolved or every required detector exists.
- `/admin/activity-log` is read-only, with demonstrated action filter and server pagination. Known admin actions link to safe implemented workspaces. Arbitrary backend paths never become navigation URLs. IPs, arbitrary details, notes, passwords/tokens and reporter identity on report-creation events are omitted. Operator attribution on admin actions is retained. Only actual backend records are shown; no substitute local audit history is generated.
- New console pages/actions are Super-only according to the implementation matrix. Fresh `users.view`/`users.manage` gates are conservative compatibility checks using the only supplied permission vocabulary; Support safety CSV access from Step 8 is unchanged. Real granular permissions remain C01.
- Overview links now open the safety and alerts workspaces. Existing global safety/activity CSVs are reachable with explicit unfiltered semantics; documented list filters are not silently applied to an export endpoint that has no filter contract. All-status list selections omit those filters and enable the unfiltered CSV action.
- Existing LMS sessions, learning/progress, school/class membership, family links, content, review, visibility and finance are preserved. Existing backend media uploads continue to work; report-purpose uploads must go through the new dedicated workflow.

## Screenshot privacy configuration

Screenshots are **disabled by default**. The supplied upload example exposes a public-looking source path containing the reporter ID. No private read/preview endpoint is supplied. Users see an explanation and can submit reports without screenshots; admins see attached media IDs without links/previews.

The implemented optional path is POST `/api/safety/media/upload`, server-mediated to POST `/media/upload` with purpose forcibly set to `report`. It supports up to five PNG/JPEG/WebP screenshots, 4 MB each (existing proxy limit, not acceptance of the PRD's larger upload limit), checks signatures and returned image/purpose/owner, strips URLs, and issues a signed 30-minute receipt bound to the encrypted session and media ID. Submission accepts only those matching receipts. Another session, forged ID or expired receipt is refused. Backend ownership/attachment validation is still required.

Only after confirming private backend storage, direct-URL denial, authorized retrieval and lifecycle policy may a deployment set `SAFETY_REPORT_PRIVATE_ATTACHMENTS=true` in its server environment. That flag enables the already implemented upload/form path; it does **not** make public backend storage private or provide a missing private preview endpoint. Unused upload deletion, file scanning, larger-size transport and private preview remain C05.

## What to test

1. As learner and parent, open Report a concern. Follow a course/class/teacher/school report link where available and verify the correct ID. Submit a concern, record the reference and refresh My reports. Try invalid targets/reasons and another account's history; no unrelated report or internal identity/note should be disclosed. Screenshots should be unavailable under the default configuration.
2. As Super Admin, open Safety reports, compare priority/due time/overdue state against the backend and switch between unresolved/all statuses. Open a report, assign an active authorized admin and add a comment. Refresh and verify actual assignee/comment/operator/time. Wrong assignee, stale/resolved report, missing/revoked grant and other roles must be denied.
3. Resolve an isolated test report using a returned outcome and reason; confirm the reference. Verify saved outcome/time/operator, then refresh the reporter's history to see Handled. Independently verify the target-specific effect and actual reporter notification on the real backend. A report about the current admin's own target must require another admin. Interrupt a request and reconcile records before repeating it.
4. Open Alerts, inspect only returned signals, acknowledge one with a note and refresh the Acknowledged list. All statuses must show both open and acknowledged records. Verify the actual actor and note; no UI should claim acknowledgement resolved the issue.
5. Open Activity log, filter a demonstrated action such as `verification`, paginate and check real backend attribution. Test related links and make sure no edit/delete controls or credentials/private notes appear. Unfiltered CSVs are separate from filtered list views; verify their actual authorized/redacted content before release.
6. After private backend delivery is approved and configured, test screenshot upload, another session's/forged/expired attachment receipt, MIME mismatch, size bounds, direct source URL denial and authorized admin retrieval. Enabling the flag alone does not pass privacy acceptance. Recheck existing lessons, quizzes, progress, assignments, parent linking and prior admin actions, plus keyboard/tablet/light/dark behavior.

The supplied examples prove some records exist, not complete protected capture. Full text/email/date search and unsupported log filters remain unavailable.
